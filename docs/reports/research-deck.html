Gates that hold

An AI-assisted development lifecycle for NBN Co: grounded in published practice, built three ways, reviewed independently. The research behind it.

Team 2: Sidney Zeng, Ahmed Falulur Rahuman, Zac Clarkson, Zafir Hasan, Chirag Wadehra
Supervisor Ben Philip · Client representative Alessio Bonti · github.com/Peepachuu/nbn-sdlc-demo
The research in one slide

Question, method, result

NBN asked for a lifecycle with a traffic light on each of eight stages. A colour per stage cannot be acted on, and the evidence says AI-written code passes its own tests at rates that make green CI an unsafe gate.

We opened the stages into 44 tasks, each with a colour (who decides), a gate (what must be true) and a holder (what makes it hold). We grounded it in 63 audited citations, tested it against two interviews, built the gates into a repository, and ran a pre-registered trial: one brief, one base, three methods, a reviewer who built none of them.

The registered hypothesis was not supported. What differed was kind: two builds met twelve of fourteen criteria, passed every check and stored nothing; the gated build met fourteen, held eighteen attacks, and had the test that caught the ownership fault. No automated gate caught the missing data store. A human gate did.

Three practices taught
Write the issue with acceptance criteria. State what is out of scope. Separate the instructing role from the building role.

"As you build the environment and the environment learns from you, you can slowly move some of those yellow tasks into the green area."

Facilitator, tying the colours to the repository's rules file. D2 section 4.

"The question would be, are all the tests correct?"

The problem

An agent that writes the tests passes its own tests

24.2%

of AI-introduced issues still present at repository head; security issues survive most (41.1%). Liu et al. 2026, 304,362 AI-authored commits.

39 to 59%

of LLM-generated test assertions correct, across two datasets. Zhang et al., ACM TOSEM 2025.

45%

of security-relevant tasks where models chose the insecure option. Veracode 2025, vendor report; Pearce et al. (CACM 2025) found about 40% of Copilot programs vulnerable.

Three gaps in the baseline. A colour per stage is a policy without a procedure. Green CI is not a safe gate. And most AI "rules" in a repository are text an agent is asked to read.

Research questions

Three questions

RQ1

Can the eight-stage colour scheme be grounded at task level in published engineering practice, and does it survive that contact?

RQ2

What mechanisms can hold a gate in a GitHub repository, and which hold against an AI agent as well as against a person?

RQ3

On the same feature, from the same brief and base, does the gated lifecycle change what ships compared with an AI-only build and a copy-and-paste build?

Hypothesis, registered 12 Oct 2026 · 48fff18

H1, as committed

"On the bigger feature, the three builds will end up further apart than they did in trial one, by more than the feature grew."

Measurement

Spread on a measure is the highest build's result minus the lowest, divided by feature size: 10 criteria in trial one, 14 in trial two. Three measures decide: issues that escaped review, feature criteria not met, active human minutes.

Pass condition

Supported if trial two's spread per criterion is higher on at least two of the three. Expected directions were written down and are not part of the test. Either result is an observation, not a rate.

Empirical evidence

Contested on speed, one way on quality

Speed

Peng et al. 2023: 55.8% faster on a bounded task (RCT, n = 95 freelancers). Cui et al. 2025: 26.08% more pull requests (three firms, n = 4,867). METR 2025: 19% slower on mature repositories while believing 20% faster (RCT, n = 16). GitHub's own RCT: small authoring-quality gains, self-reported.

Flags we carry: the pro-AI trial used an artificial task; the anti-AI trial calls itself a snapshot; the vendor trial is the vendor's.

Quality and tests

Veracode: insecure option 45% of the time, Java 72%, XSS 86%. Apiiro: CVSS 7+ findings about 2.5 times more frequent. Pearce: about 40% vulnerable. Method · the map

Three attributes per task, six holders

Colour
Who decides. Red: a human. Amber: AI drafts, a human approves. Green: AI runs, a deterministic check holds.
Gate
A countable condition that must be true before the next task starts.
Holder
What makes the gate hold. Hook (git) · Hook (agent) · CI check (required) · CI check (advisory) · Platform rule · Human. And the label for the absence of one: No gate.
Scope (ADR-002)
Stages 6 and 7 in full; 5 and 8 to their handoffs; stages 1 to 4 as an entry gate of four artefacts. Reason: the evidence concentrates where AI writes and ships code, and five people cannot specify eight stages to operational depth in two sprints.

The rule a green row must meet

A green task without a hook, a check or a rule named is an amber task mislabelled. Instruction files, prompt files, skills and an agent's own summary are No gate: whether an agent complies with them is up to the agent.

Method · the review protocol, committed 17 Oct

Same checks, same order, every build

17

test jobs, one per criterion, each with a pass condition and an evidence file name

18

attacks in a fixed order: cross-requester reads and writes, forged owner, forged match, no valid match, invalid status, double submit, hard delete, out-of-scope surfaces, default deny, signed out, keyboard, colour, secrets, dependencies, fresh clone, declaration

1 + 2

one mutation run per build, formula stated, no threshold; two seeded faults applied by hand: S1 owner check removed, S2 access-equipment check always passes

9 × 3

finding categories and severities fixed in advance; review order by pull-request opening time; nothing read from one build into the next

The reviewer is a team member who wrote the map and the protocol and built none of the three. That is a limitation, stated, and the pre-commitment is what constrains it.

Part four

What we found

RQ1 the map. RQ2 the holders. RQ3 the trial. Then the hypothesis.

RQ1 · the map

44 tasks. 16 red, 16 amber, 12 green.

What changed from the baseline: stage 2, the workshop's only green, became mixed on the requirements evidence (drafting stays green, criteria amber, anchors and acceptance red); stage 4's journey mapping went amber; stages 5 to 7 were confirmed amber overall and split into tasks of all three colours; stage 8, unreached at the workshop, is green for preview and rollout mechanics, amber for monitoring, red for promotion and incidents. The stage order held as a taxonomy of concerns, not a sequence.

RQ2 · what holds a gate

Three things we established by running them

  • A git hook binds every tool and every person who installed the repository. A person can skip it with --no-verify. The agent hook closes that for the agent and tells it why.
  • An agent hook binds only the tool it is installed in and fails open after its timeout. Nothing binds a chat window in a browser. Lane B had the git hooks and nothing else.
  • Instruction files are not gates. In the dry run of the plan-approval step, the agent "stopped and waited for approval" as asked, and the record says the gate "was demonstrated through agent behaviour, not through a deterministic enforcement mechanism".

On main today

CLAUDE.md titles its instruction text "Mandatory AI Development Gates". By the taxonomy it is No gate. Listed as an open correction.

Ruleset, main vs trial

The team's shared repository requires only AI Declaration. The trial template required all six, but only lane B kept that ruleset; lanes A and C built in a fresh repository and a fork with none. The six-check gate was proved on one trial repository.

5
Part five

What it means

What the count missed, which holders did the work, and what is weak.

Discussion

The count tied. The kind did not.

What the measure saw

Four escaped issues per lane. A missing screenshot and a missing persistence layer each count one.

What a reader sees

Two lanes shipped a feature that met twelve criteria on screen, passed six checks, carried a correct AI declaration, and had no data store. One lane persisted every request, refused every forged call, and had written the ownership test before the fault was seeded.

The prediction asked whether the gap would widen. The data answers where the gap sits: at the plan approval (6.1), where a reviewer asks where the data goes, and at the test judgement (7.4), where a reviewer reloads the page. Methods A and B do not have those gates. Method C does, and its builder also wrote the data design the gates then protected.

Discussion

Which holders did the work

In lane C, by how often they fired

  1. The base's default-deny Firestore rules: every direct access.
  2. The Server Action's re-check of owner, status and match inside a transaction: every forged call.
  3. The zod strict schema: extra fields.
  4. The session check with redirect: signed out.

The hooks and CI

Caught nothing in any lane. Every builder complied with them. What they bought was comparability: three Conventional histories, three declared agents, three fresh-clone runs with the same result, and one disagreement about a model name that would otherwise be invisible.

An automated gate that never fires is not evidence it holds. It is evidence that nobody tried the door.

Discussion

What the gates buy

The client's thesis, tested

A stage moves to green with automated checks or more context. Checks held in every lane. Context did not: the plan-first instruction files were honoured by choice in the dry run and removed in lane A without consequence. Green needs a holder; nothing an agent is asked to read counts.

Review yield, not review time

About 70, 60 and 75 reviewer minutes per lane. In A and B the hour bought a defect list headed by a missing data store. In C it confirmed 14 criteria, 18 attacks and a caught seed. Same hour, different purchase.

Two unfinished features

Nine minutes bought a build that forgets everything on reload. The unit that matters is time to a correct feature, and the rework cycle was not measured. Trial one: the cheapest build per criterion let the most through.

Where review does get lighter

The mechanical part moved to machines: format, lint, secrets, commit form, declaration, trailer, typecheck, tests, audit. The human keeps two judgements. And smaller diffs: lane A rebuilt the home page nobody asked for. Not measured per lane; not claimed.

The lifecycle does not remove the price of reviewing AI output. It stops the price being paid for a build that fails the brief.

Threats to validity

What is weak, in our words first

Internal

One builder per method: builder and method cannot be separated. Lane C's builder authored the gated method. The reviewer built none of the three but wrote the map and the protocol; the protocol, the decision-5 marking and the frozen heads were committed before any build was read. Builders prepared their own start states with the PM's agreement; recorded as dated amendments.

Construct

An escaped issue counts as one whatever its severity. The trial one baseline was written from memory. The keyboard criterion was checked in part. The first mutation attempts were invalid for a configuration reason, recorded and rerun.

External

Three builds, one feature, four-hour windows, student plans, no NBN developer interviewed. Stages 1 to 4 and 8.2 to 8.6 are mapped and cited and were never run. Observations, not rates.

Also open: the six-check gate was proved on the trial repositories, not the shared one; the hourly rate behind every cost figure was never agreed with the client; two repository files overstate enforcement and are listed for correction; two verdicts in the map are "source silent" and say so.

Part six

What a team takes away

Install once. Decide four things every time.

Conclusion

Install once, decide four things every time

Install once

The git hooks, the agent hook, the six CI checks, the pull request template, the ruleset. All files in the repository, except the ruleset, which belongs to the repository and does not follow the code. The manual's section 3 lists each with its path.

Decide every time

  1. The issue has testable criteria and an out-of-scope list (5.3).
  2. No code before an approved plan (6.1).
  3. Two people who did not write it approve (6.4).
  4. Someone asks whether the tests would fail if the code were wrong, and reloads the page (7.4).

A traffic light belongs on the task and must name what holds it, or it is a wish.
