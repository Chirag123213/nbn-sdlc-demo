## 1. In one paragraph

This is the independent review record for the lane C (gated framework) build by Zafir Hasan, reviewed against the frozen commit `40c65f5` and never against anything pushed later. Every feature criterion passes on the preview. Each request is written to Firestore through a Server Action that checks the session, and scheduling runs in a transaction that checks the owner, the status and the match again. All eighteen attacks held: the Firestore rules deny every direct read, write and delete from the browser, signed in or not; the Server Action refuses an incompatible technician, a request with no valid combination, a second schedule, an unknown id, extra fields, and another requester's request without revealing that it exists; the signed-out call never reaches the action. Both seeds are caught. The matching function and the actions are well tested (86 percent of action mutants killed); the component and the zod schemas less so. The findings are all record and test-quality items, none of them in a row that counts toward the prediction except the mutation score.

#### 3.4 What this does not show

- Keyboard operation of the native datetime-local and radio controls was not exercised; the pass on TJ13 rests on the controls being native inputs with labels and no custom handlers.
- AT15 is partial, as for the other lanes.
- The direct Firestore probes used the REST API with ID tokens from the Identity Toolkit sign-in endpoint rather than the web SDK; the rules evaluation is the same. A read of the requester's own `users` document was also denied, which is base behaviour and was not pursued.
- The mutation score covers the configured scope, which includes untouched base files; both figures are given. `catalog.ts` (the fixture loader) has 14 surviving mutants and no test, which is the build's, not the base's.
- There is no screen on which a requester can see an earlier request. AC01's "visible afterwards" is met by the server reading the record back. The criterion does not name a screen, so this is recorded as a note rather than a fail.

#### 3.5 What the manual takes from it

- Server Actions that re-run the match, check the owner and check the status inside a transaction turned every forged request into a refusal, and the base's default-deny rules did the rest. None of that needed a rules change. The pattern to write down is: no client read or write path for feature data unless the brief asks for one.
- One test, "rejects a cross-owner scheduling attempt without revealing the request", is the whole reason seed S1 was caught. A tests-first gate produced it; the two other lanes have no equivalent because they have no owner.
- `tabindex="0"` on a card that already holds a radio is the kind of thing a keyboard run catches and a checklist does not.
