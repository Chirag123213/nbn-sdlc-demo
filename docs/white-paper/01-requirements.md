## 1. In one paragraph

A developer needs an agreed brief, examples of acceptable behaviour and a way to check the result before asking AI to build a feature. This chapter links the client's requested outputs to the team's requirements and the evidence from its practical work. It separates a working screen, a saved record, a passing automated test and independent acceptance. The Trial Two reviewer reports different outcomes from the builders on saving requests; this draft preserves that disagreement so a named person can resolve it without changing the frozen brief.

#### The AC01/AC11 disagreement

The frozen wording says AC01 allows a requester to “create a technician-dispatch request for a customer premises”. AC11 says a scheduled dispatch “records the selected technician, the scheduled visit details and the equipment or access requirement used for the match” ([frozen brief][Frozen]). It does not expressly say to retain the data after refresh, name a database, require sign-in, or provide a previous-request screen.

The A/B builders read the brief as allowing an in-memory browser flow and marked those criteria passed. The [A][A] and [B][B] independent review records explain that interpretation and the observed absence of storage. The reviewer used the [test protocol][Protocol], whose TJ01 asks for a request visible afterwards and TJ11 checks both the UI and stored record. Under that reading A/B fail AC01 and AC11; C passes, with a note that its saved records are read back through the server rather than a history screen.

Both positions must remain visible. The chapter reports the reviewer's 12/12/14 counts, without treating the stronger storage interpretation as an uncontested original requirement. Sidney Zeng is the named owner in the lane records for resolving acceptance/reporting, with Ahmed supplying the requirements wording and Zac the protocol evidence. Any decision needs a dated rationale and an explanation of whether the protocol clarified the brief or added an expectation. Keep the frozen inputs and reviewed commits unchanged and report the decision beside the result.

The protocol also tests unauthenticated access. Lane A's public route is an attack finding, not an additional numbered criterion failed in the feature total. The [review index][Index] gives four prediction-counted findings per lane, while A's opening paragraph says three. The findings tables say four. This inconsistency is flagged for Zac and Sidney; this chapter does not issue a prediction verdict from it.

- Identical starting conditions: setup changes, moved repositories and rulesets are documented in [the protocol][Protocol].
- A fresh application test by this authoring session. Results above retain the original review date, tooling and limitations.

### 3.5 What the manual takes from it

These are recommendations from the traceability review, not retroactive additions to the frozen trial.

- **Task 5.3:** define what “create”, “record” and “afterwards” mean. For a future brief, state whether a record survives reload, who can retrieve it and an example that proves it.
- **Task 5.3:** approve the acceptance test alongside the requirement. Keep numbered behaviour separate from evidence-format rules and from additional adversarial checks.
- **Task 6.1:** identify business context, approved criteria, exclusions and the exact starting revision before requesting an implementation plan. Record agreed clarifications before a comparison starts.
- **Task 7.1:** map every criterion to an actual check and reachable evidence. A builder's tick, shared screenshot or green test suite is not independent acceptance.
- **Task 7.4:** report which tests ran live, which used mocks and which remain incomplete. Record the method used to judge test strength without inventing a threshold.
- **Task 6.4:** have the reviewer record disagreements and a named decision owner. Preserve the failed result and reviewed commit even if a later build fixes it.
